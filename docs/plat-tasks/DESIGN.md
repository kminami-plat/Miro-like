# 今日のボード 設計メモ（plat-todo の第 2 クライアント）

## 画面の流れ

サインイン → **今日のボード**（`/`、社員 × ステータスの固定グリッド、付箋 1 枚 = plat-todo のタスク 1 件）
→ 必要なら **アーカイブ**（`/archive` の営業日カレンダー → `/archive/<日付>` の閲覧専用ボード）。
従来のダッシュボード・ボード作成・自由キャンバスはコードを残して無効化（`LEGACY_BOARDS=1` で復活）。

## プラットフォームとホスティング

**このホワイトボードアプリ（FastAPI）がボードを配信し、サーバー側が plat-kv の第 2 クライアントになる。**

```
ブラウザ ──(同一オリジン, wb_session Cookie)──▶ FastAPI /api/plat/* ──(X-Plat-Token)──▶ plat-kv.k-oda.workers.dev/kv/<key>
                                               │
                                               └─(CF-Access サービストークン or ローカルコピー)─▶ people / domains / projects.json
```

- **CORS**: ブラウザは自分のオリジン（Render など）にしか通信しない。Worker を呼ぶのはサーバーなので
  CORS の対象外。Worker の許可オリジンを変える必要はない。
- **認証**: 書き込みトークンはサーバーの環境変数 `PLAT_KV_TOKEN`（ローカルは `.env`、本番は Render の
  ダッシュボード）にだけ置く。ブラウザにもリポジトリにも出ない。`/api/plat/*` はホワイトボードに
  サインイン済みのユーザーだけが使える（ゲストは不可）。トークン未設定なら自動的に閲覧のみになる。
- **参照データ**: `pm.plat-yonezawa.com` は Cloudflare Access の内側にあり、外から取ると 302 でログイン
  画面に飛ばされる（実測）。そこで次の順で読む:
  ① `PLAT_ACCESS_CLIENT_ID/SECRET`（Access のサービストークン）があれば取得
  ② なければ `data/plat/*.json`（ローカルコピー）
  ③ どちらもなければ、タスクの担当者 ID から行を作る
  people は一切書き込まない。10 分キャッシュ。

## コンポーネント構成

| ファイル | 役割 |
| --- | --- |
| `server/plat_tasks.py` | **データ層（サーバー）**。`KvClient`（GET/PUT）、`TaskStore.load() / save_task() / delete_task() / apply()`、業務ルール（open/overdue/heavy、done_at）、プロジェクト日程の読み込み、参照データ。FastAPI に依存しない |
| `server/archive.py` | 日本の営業日カレンダー、1 営業日 1 件の記録（`board_archives` テーブル）、31 日で削除 |
| `server/main.py` | 薄いルート: `GET /api/plat/meta`, `PUT /api/plat/roster`, `GET /api/plat/tasks`, `POST /api/plat/tasks/batch`, `GET /api/archives[/<日付>]`, `POST /api/archive/run` |
| `static/plat_store.js` | **データ層（ブラウザ）**。`load() / createTask() / saveTask() / deleteTask()`、送信キュー、1.5 秒のデバウンス、再試行、localStorage への未送信分の退避、フォーカス時と 60 秒ごとの再読込。DOM に触れない |
| `static/tasks.js` | UI のみ。`TaskGrid(container, opts)`。グリッド、付箋（その場で書き換え）、インライン追加、ドラッグ、詳細モーダル、フィルター、行サマリー、行の編集。`opts.archive` を渡すと `PlatTaskStore.frozen()` で閲覧専用に描く |
| `static/app.js` | ルーティング（`/`、`/archive`、`/archive/<日付>`）、アーカイブのカレンダー |

## 保存とマージの方針

PUT は値全体を置き換え、既存ページも同時に書くので、**1 回の保存 = 最新を GET → 自分の変更だけ適用 → PUT**。

1. ブラウザは編集を即座に画面へ反映し、タスク ID ごとにキューへ積む。更新は**変わったフィールドだけ**を持つ
   （例: ドラッグなら `status` だけ）。1.5 秒以内の連続操作は 1 回のバッチにまとまる。
2. サーバーは `apply(ops)` で、直前に取得した最新ドキュメントに ID 一致で変更を当て、1 回だけ PUT する。
   同一プロセス内の書き込みはロックで直列化（ホワイトボード利用者同士は競合しない）。
3. 他人のタスク、`suggestions`、未知のトップレベルキー、タスク内の未知フィールド（`programId`、
   `milestoneId`、`createdAt` など）はそのまま残る。`status` が `完了` になったら `done_at` = 今日
   （ブラウザのローカル日付）、それ以外に戻したら `null`。
4. 安全弁: GET が失敗・形式不正なら書かない。本番キーが空（`null`）で返ってきたら書かない。
   更新しようとしたタスクが他所で削除されていたら復活させずに通知。タイトルが空のタスクは保存しない
   （空の付箋はデータにならない）。
5. PUT が失敗したら変更はキューに残り（localStorage にも保存）、画面上部に「保存できていない変更 n 件」
   と表示し、3 → 10 → 30 → 60 秒間隔で再試行。「今すぐ再試行」ボタンもある。作成は ID を先に決めて
   送るので、応答が失われて再送されても二重にならない。

## アーカイブ（営業日ごとの記録）

- 記録の中身は画像ではなくデータ: その時点のタスク・日程タスク・行（名簿）・参照リストの JSON。
  閲覧時は今日のボードと同じ描画コードで閲覧専用に描き直す（`PlatTaskStore.frozen()`）ので、見た目は
  当時のまま、文字はコピーでき、フィルターも効く。期限切れはその日の日付で判定する
- `ensure_captured()` は「締め時刻を過ぎた直近の営業日」に記録がなければ 1 件作るだけの冪等な関数で、
  ①サーバー内の 1 分ごとのループ、②このアプリからの書き込みの**直前**、③外部 cron（`POST /api/archive/run`）
  から呼ばれる。②により、締め後にこのアプリで行った編集は前日の記録に混ざらない
- 記録時刻が締めから 30 分以上遅れたら `late` を立て、画面に実際の記録時刻を出す（黙って不正確にしない）。
  Render 無料プランのようにサーバーが寝る環境では③の外部 cron を推奨
- 保存は同じ DB（SQLite / PostgreSQL）の `board_archives`。1 日分は数十 KB 程度で、31 日で削除

**残るリスク**: Worker に条件付き書き込み（ETag 等）がないため、サーバーの GET と PUT の間（数百 ms）に
既存ページが保存すると、その変更を上書きしうる。また既存ページが「読み込み時点の一覧を丸ごと PUT」する
作りなら、そのページを開いたままの人が保存したとき、こちらの変更が消えうる（既存ページ側の挙動なので
こちらでは防げない。検証チェックリストの B-4 で確認する）。根本対策は Worker 側の版番号チェックだが、
フェーズ 1 の範囲外。
